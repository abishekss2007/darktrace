## 7.1 Uniswap Foundation

In [`/contracts/src/DarkTraceHook.sol`](../../contracts/src/DarkTraceHook.sol), I implemented `IHooks` with `beforeSwap` and `afterSwap` permissions and mined a CREATE2 salt (`0x139d` via Foundry's canonical `CREATE2_DEPLOYER` `0x4e59b44847b379578588920cA78FbF26c0B4956C`) so the deployed hook address (`0xBCC9e1C474Ed195b3791f2c41EdAC2a25c5b80c0`) satisfies the `0x00C0` flag bitmask. Inside `beforeSwap`, the hook reads `poolManager.getSlot0(poolId)` and records the pre-swap tick into Cancun transient storage (`tstore` at slot `keccak256(abi.encode(poolId, "darktrace.tstore.pretick"))`), while `afterSwap` computes the realized `tickDelta` without mutating swap deltas or blocking order flow. Because `afterSwap` executes after a single swap and cannot see future swaps in the block, our hook is strictly an attribution engine (`ExtractionDetected`), not a pre-trade prevention filter. The hardest engineering friction in `DarkTraceHook.sol` (`lines 29–36` and `257–301`) was that EIP-1153 transient storage clears at the end of each transaction, whereas a sandwich attack spans three separate transactions (searcher frontrun, victim swap, searcher backrun) within the same block. Relying on `tstore` alone works for multi-swap router batching within one transaction, but cross-transaction intra-block detection required bit-packing `PoolTransientState` (`lastBlock`, `lastDirection`, `lastTickDelta`, `frontrunTickDelta`, `lastSender`, `victimCandidate`) across two 256-bit slots (`stateA`, `stateB`) with a `tload`-to-`sload` fallback (`if iszero(valA) { valA := sload(slotA) }`), plus storing `frontrunTickDelta` separately so the victim swap did not overwrite the searcher's initial push delta. **Feature request**: I would love an optional `afterBlock` checkpoint callback on `PoolManager`—or a canonical v4 transient-checkpoint pattern for block-scoped state—so multi-transaction intra-block MEV hooks do not need `sstore` fallbacks across transaction boundaries.

## 7.2 Arc

We built DarkTrace's restitution layer on Arc Testnet (`Chain ID 5042002`) because LP MEV rebates only work economically when payouts settle in native USDC with predictable, sub-cent execution costs that do not consume small per-swap claims like our `$1.25 USDC` demo rebates. In our architecture, we split attestation from custody across two contracts: [`/contracts/src/SimulationRegistry.sol`](../../contracts/src/SimulationRegistry.sol) (`0xb8416cb4d82BA72b70C3EC55d7AC66b5DB415CF8`) stores authenticated `(simulationHash, receiptHash, extractedUSDC, blockNumber)` records written by our off-chain counterfactual engine, while [`/contracts/src/RebateVault.sol`](../../contracts/src/RebateVault.sol) (`0x2ab745F51002Ce236A9A2dA81cDaA553B87f28CD`) holds pre-funded USDC (`5.00 USDC` on-chain) and verifies `SimulationRegistry.getAttestation(receiptHash)` plus a `claimedReceipts[receiptHash]` replay nullifier before transferring USDC to the LP. We explicitly did not attempt synchronous or same-transaction cross-chain settlement between Base Sepolia and Arc; Base Sepolia searcher bond reduction and Arc pre-funded vault restitution run as two independent, asynchronous flows. Our main friction point during deployment (`contracts/script/DeployArcTestnet.s.sol`) was navigating the distinction between Arc's native gas asset and the ERC-20 USDC interface at `0x3600000000000000000000000000000000000000`. When broadcasting our deployment with Foundry, we hit `error code -32003: insufficient funds for gas * price + value` because native gas estimation in `forge script` uses 18-decimal EVM wei semantics (`0.044 ETH` estimated at `43.5 gwei`), whereas `IERC20(0x3600...).transfer()` inside `RebateVault.sol` operates on 6-decimal USDC units (`5_000_000` = `5.00 USDC`). **Feature request**: Please add a canonical *"Gas-Token vs. `0x3600...` ERC-20 Interface"* snippet to the Arc documentation—along with a typed viem/Foundry helper—showing how 18-decimal gas accounting maps to 6-decimal ERC-20 transfers during deployment and vault funding.

## 7.3 Arkiv

In [`/lib/arkiv/client.ts`](../../lib/arkiv/client.ts) and [`/lib/arkiv/schemas.ts`](../../lib/arkiv/schemas.ts), we structured all forensic records under the `darktrace.v1` namespace across three schemas: `ExtractionReceipt`, `SearcherProfile`, and `LPClaim`. Arkiv is load-bearing in DarkTrace because an on-chain vault (`RebateVault.sol`) only verifies a 32-byte `receiptHash` nullifier, whereas LPs, hook operators, and order-flow routers need a queryable ledger indexed by `poolId`, `searcher`, and `victim` rather than scanning thousands of raw Base Sepolia event blocks. While writing the adapter in [`/lib/arkiv/client.ts`](../../lib/arkiv/client.ts), the hardest detail to get right was guaranteeing that the off-chain Arkiv entity identifier (`const entityId = `${this.namespace}:receipt:${hash}`;` at `lib/arkiv/client.ts:42`) and the on-chain `bytes32 receiptHash` attested in `SimulationRegistry.sol` never diverged. In `computeReceiptHash` (`lib/arkiv/schemas.ts:38–56`), we had to enforce deterministic JSON key ordering and strict lowercase normalization (`txHashes: receipt.txHashes.map((h) => h.toLowerCase())` at `lib/arkiv/schemas.ts:51`); a single EIP-55 checksum mismatch or reordered property changed the `keccak256` digest and caused `RebateVault.claimRebate` to revert with `UnverifiedSimulation`. Additionally, because we lacked an official typed npm client with local mock fixtures for `arkiv_putEntity` and `arkiv_queryEntities` (`lib/arkiv/client.ts:46,77`), we built an in-memory map fallback (`memoryReceipts`, `memoryProfiles`, `memoryClaims`) so unit tests and `/api/stats` remain deterministic offline. **Feature request**: Please ship a typed `@arkiv/sdk` helper that provides built-in canonical JSON/EIP-712 hashing for entity payloads plus documented query-pattern examples for multi-index queries such as *"get all `ExtractionReceipt` records for a `searcher` across all `poolId`s under `darktrace.v1`"*.
